Anatomy of a Specialist Call — Skill + Tools, worked example

how a sub-question becomes a grounded finding
Reviewer asks
"How did the model scores react this past year?"
→ orchestrator routes the sub-question to BaseSpec · modeling
Domain skill (inline prompt)
skills/domain/modeling.md
Domain knowledge the specialist needs to interpret what it queries — score-to-column maps, thresholds, and a discipline cap.
Score → column mapping
  • CDSS → credit_loss_prob
  • TSR → tot_struct_risk_score
  • Quote both: "CDSS (credit_loss_prob): X"
Presentation discipline
"Scores + thresholds together — TSR reached 39.6 in 2024-09 (risky: > 20). Never cite a value alone."
Fast lane (≤ 2 rounds)
  • For "how did CDSS/TSR react" → ONE batch_summarize_trend
  • Hard cap: 2 tool calls.
  • Don't pre-schema model_scores — column names known
Workflow skill (inline prompt)
skills/workflow/data_query.md
Analytical workflow shared by every BaseSpec — round budget, batching discipline, stop conditions, output rules.
Round budget (hard cap: 6)
  • Narrow → 2 rounds
  • Trend / breakdown → 3–4 rounds
  • Round 5+ is a smell — emit partial output
Batch upfront
"Before any summarize_trend, ask: will I want any OTHER metric too? If yes, use batch_summarize_trend in one call."
Anti-hallucination
  • Every claim in findings traces to a tool result THIS run produced
  • Uncertainty → data_gaps, never filler
  • raw_data: { table : [row, …] } — empty {} is honest

R1
tool call · batched up-front (modeling fast lane)
~ one round, ~30s wall-clock
batch_summarize_trend('''[
  {"table_name":    "model_scores",
   "value_column": "credit_loss_prob",        # CDSS
   "time_column":  "trans_month",
   "period": "month", "op": "max"},
  {"table_name":    "model_scores",
   "value_column": "tot_struct_risk_score",   # TSR
   "time_column":  "trans_month",
   "period": "month", "op": "max"}
]''')
→ returns 12-month series per score · thresholds attached from catalog
   (credit_loss_prob risky > 0.5, tot_struct_risk_score risky > 20)
▸ Why batched. data_query.md says "before any summarize_trend, ask: will I want another metric?" — yes, both scores, so one call.
▸ Why this tool. modeling.md's fast lane prescribes batch_summarize_trend verbatim for "how did CDSS/TSR react".
▸ No schema probe. Column names are domain-known — modeling.md forbids re-probing model_scores.
R2
SpecialistOutput · grounded findings
charts render automatically
finding CDSS (credit_loss_prob) climbed from 0.12 (2024-11) to 0.61 (2025-04), crossing the 0.5 risky threshold in 2025-03.
finding TSR (tot_struct_risk_score) rose from 22.0 to 28.5 over the same window, breaching the catalog threshold of 20 from 2024-12 onward.
evidence batch_summarize_trend · 12 rows · ref. trans_month 2024-05 … 2025-04.
data_gaps No CDSS / TSR values prior to 2024-05 in this case; pre-window inferences unsupported.
▸ Why this shape. modeling.md's "scores + thresholds together" rule — every value paired with its catalog threshold.
▸ Why uncertainty surfaces. data_query.md's anti-hallucination rule routes gaps to data_gaps rather than filling.
▸ What happens next. The async distiller (§ memory-mgmt) extracts a multi-series internal_model_scores_trend KP into the session KB — next turn's modeling question hits a warm specialist.
